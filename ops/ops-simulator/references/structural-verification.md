# 结构核验（Structural Verification）

读仿真与编译产物，回答一个**和性能无关**的问题：**声称的结构到底有没有被构建出来。**

**定位**：
- 流水空泡分析（`pipeline-bubble-analysis.md`）回答「主 pipeline 为什么 idle」—— 性能**为什么**差。
- 本文回答「这份实现有没有按设计建出那个结构」—— **在任何性能数出来之前**就能判。

两者正交。一个实现可以流水很干净而结构完全不是设计要的那个（退化回退），这种情况下性能分析会一路向下找原因，而结构核验一眼就能看出来。

**使用时机**：
- 设计里写了「A 操作数走寄存器源」「双缓冲深度 2」「同步用 SetFlag/WaitFlag 成对」这类**结构性断言**，要在上板之前确认它成立
- 性能没达标，而占比/停顿指标全在正常带内 —— 怀疑结构没落地
- 做 A/B 对比时要确认「这次改动真的改到了编译产物」，而不是改了注释或被编译器消掉了

---

## 为什么需要这一层

性能计数器看不到结构。一个具体的翻车模式：

> 设计判定矩阵乘的 A 操作数走寄存器源（RS），而验收只查寄存器用量。
> 于是一个「预留了寄存器预算、但操作数仍然走共享内存往返」的退化实现
> **通过了验收并被当成设计落地**。
>
> 预算留出来了，路径没建起来 —— 这两件事在寄存器用量上无法区分。

同类形态还有：声明双缓冲而实际是单缓冲回退；声明 L1 常驻而数据每次从 GM 重读；声明同步成对而少了一侧。这些在聚合计数器上都表现为「某个占比偏高」，而那个症状有十几种成因。

## 三条通道

按**代价从低到高**排。前两条都在本 skill 已有的采集产物里，第三条不需要仿真器。

| 通道 | 能判什么 | 需要什么 | 代价 |
|---|---|---|---|
| A. 静态 IR（`ccec -emit-llvm`） | 操作数所在存储、同步 intrinsic 是否成对 | 只要 CANN toolkit | 秒级，无硬件无仿真器 |
| B. `instr_exe.csv` 的 `pipe` / `detail` 两列 | 搬运的源与目的、走了哪条 pipe | 一次仿真（本 skill 已在采） | 跟仿真同价 |
| C. `ub.{rd,wr}_log.dump` | UB 的逐条读写地址 | 一次 CAModel 仿真 | 同上，文件更大 |

---

## 通道 A：静态 IR —— 地址空间就是操作数来源

毕昇编译器可以停在 LLVM IR，而 IR 里**地址空间直接编码了操作数所在的存储**。

```bash
# 产出 device 侧 .bc，再反汇编成可读 IR
ccec --cce-aicore-arch=dav-c220-vec -xcce -std=c++17 \
     -emit-llvm -c -I<include> probe.cpp
llvm-dis <device>.bc -o probe.ll
```

读 `.ll` 时的判据：

| 地址空间 | 对应存储 | 读出来说明 |
|---|---|---|
| `addrspace(1)` | GM（全局内存） | 这个操作数直接来自/写向主存 |
| `addrspace(6)` | UB（Unified Buffer） | 这个操作数在 UB 上 |

举例：一条 `llvm.hivm.VGATHER.b16(ptr addrspace(6) dst, ptr addrspace(6) src, ...)` 说明源与目的都在 UB；若设计声称「从 L1 直送」而这里是 `addrspace(1)`，结构就没落地。

**边界要说清**：IR 在**指令选择与寄存器分配之前**。所以这条通道能证明「搬运路径走了哪一级存储」「同步 intrinsic 发射了几条」，**证不了**「寄存器没溢出」「调度深度是多少」。上面那个翻车案例的另一半（寄存器预算）在这条通道上仍然不可见。

**适合做门禁的理由**：不要硬件、不要仿真器、秒级，可以放在构建之后、上板之前。

## 通道 B：`instr_exe.csv` 的两列

本 skill 已经在采这个文件（见 `msopprof-simulator-guide.md` 的输出目录树）。此前它的用途是「找最耗时指令」；下面这两列是**结构判据**，与耗时无关。

官方字段表里的定义：

| 字段 | 官方解释 |
|---|---|
| `pipe` | PIPE 类型，包括指令队列（MTE1/MTE2/MTE3）和计算单元（VEC/CUBE） |
| `detail` | 指令执行的详细参数，如数据搬运的源/目的地址、长度、步幅等 |

怎么用这两列判结构：

**① 搬运路径**。`pipe` 区分了数据从哪到哪：

| pipe | 路径 | 结构含义 |
|---|---|---|
| MTE2 | GM → UB/L1 | 从主存搬入 |
| MTE1 | L1 → L0A/L0B | 搬到 Cube 的输入缓冲 |
| MTE3 | UB → GM | 搬出到主存 |

设计声称「A 操作数从 L1 直送 L0A」，那么应当看到 MTE1；若看到的是 MTE2/MTE3 的往返，就是走了共享内存绕路 —— 而这一点在寄存器用量上看不出来。

**② 搬运量与步幅**。`detail` 里有源/目的地址、长度、步幅。两件事可判：
- 声称「UB 常驻、跨 tile 复用」→ 同一段 GM 地址不应被反复搬入
- 声称「连续搬运」→ 步幅应当是连续的，而不是一堆小步幅的离散搬运

**③ 同步成对**。按 `pipe` 过滤出同步指令，检查 SetFlag 与 WaitFlag 的条数与配对关系。少一侧意味着同步缺失（可能恰好在这个 case 上不出错，但不是设计要的结构）。

```bash
# 看一个核上所有搬运类指令的 pipe 与 detail（示例，列名以实际表头为准）
awk -F',' 'NR==1 || $0 ~ /MTE[123]/' \
    msopprof_sim/OPPROF_*/simulator/core0.veccore0/core0.veccore0_instr_exe.csv
```

> `instr_exe.csv` 是**仿真**产物。官方对仿真结果的定位是「仅供参考，算子真实运行情况以实际数据为准」。
> 所以它适合做**结构判定**（某条指令在不在、走了哪条 pipe —— 这是二值事实），
> **不适合**承载数值主张（这段耗时多少 —— 那要上板数据）。

## 通道 C：UB 读写日志

CAModel 仿真会落出 UB 的逐条读写记录：

```
core0.veccore0.ub.rd_log.dump    # UB 读
core0.veccore0.ub.wr_log.dump    # UB 写
core0.veccore0.instr_log.dump    # 指令日志：cycle / PC / pipe / 编码 / 指令 ID / 助记符 / 操作数
```

`instr_log.dump` 是这三条通道里信息最全的：它带 cycle 与 PC，所以除了结构之外还能算发射间隔与 pipe 重叠（即调度深度）。

**注意**：这几个文件的名字与落盘位置**随 CANN 版本和架构变化**。`dav_2201` 上落在当前工作目录；Ascend 950 的 `cannsim` 改成了二进制 `record/instr.bin`。所以用之前先 `find` 一下实际文件名，不要照抄路径。

## 最终助记符反汇编：**不可用**

有人把实验做完了（CANN 9.1.0，`dav-c220-cube`），四条路全部关闭：

| 尝试 | 结果 |
|---|---|
| `llvm-objdump -d` 真实 `.o` | 认得 `elf64-hiipu`、能列符号与偏移，**每条指令都是 `<not available>`** |
| `llvm-objdump --version` | `hiipu64` **在** Registered Targets 里 —— 后端在，MC 反汇编表没随包发布 |
| `bisheng -cc1 ... -S` | `error: unsupported option '-S' on device side` |
| `-save-temps` | 只落 `.ccei`（预处理后的源）与 `.o`；管线里是 `-emit-obj -x cce-cpp-output`，**没有 `.s` 阶段** |

官方口径一致：毕昇编译器工具清单里**没有反汇编器**，`llvm-objdump` 的文档自述「不会打印汇编信息，仅打印符号表和偏移量」。不存在 `cce-objdump` 这个工具。

**所以**：需要「最终指令助记符文本」的分析做不了。能做的是上面三条通道 —— 它们覆盖了「结构有没有建出来」，覆盖不了「最终指令序列长什么样」。

还有一条降级手段可用于 A/B：`llvm-objcopy --dump-section .aicore_binary=` 取出 device image，再 `--dump-section .text=` 配 `xxd` 做**字节级比对**。它能回答「改了一行，二进制变没变」（用于识别空操作改动），不能做结构普查。

## 写判据时的纪律

结构核验的结论是**二值**的，不要写成程度：

| 写法 | 问题 |
|---|---|
| ✅ 「MTE1 指令存在，条数 N」 | 二值 + 计数，可核验 |
| ✅ 「同一 GM 地址被搬入 1 次」 | 可核验 |
| ❌ 「搬运看起来比较高效」 | 不可核验，等于没写 |
| ❌ 「MTE2 耗时 12us」 | 这是仿真的数值主张，不该由这条通道承载 |

另外：**结构没落地优先于改验收措辞**。如果结构核验说「声称的东西不在」，那就是实现没做到，该做的是修实现（或给实现补一条经验），不是把验收线改宽。

| 条目 | 来源 | 状态 |
|---|---|---|

第一次用之前建议先做一次确认：挑一个**已知结构**的小算子（比如明确写了 MTE1 搬运的），按通道 A 与 B 各看一遍，确认读出来的和源码里写的一致。确认过了再拿它去判未知实现。
