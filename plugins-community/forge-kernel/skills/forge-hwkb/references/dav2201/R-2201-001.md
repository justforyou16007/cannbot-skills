## 机制

把在多个 tile 或多轮循环中被重复读取的那份数据一次性搬入 UB 并保持常驻，
后续各轮直接复用，不再回 GM 取。

它省掉的是搬运次数，不是计算量。所以只有当搬运确实是瓶颈时才有收益 ——
在计算受限的 kernel 上做这件事，省下的 MTE2 时间会被 VEC 完全盖住，
总时间不动。

常驻会占住 UB，而 UB 是和 double buffer、中间缓冲争抢的同一块空间。
因此这条经验与「加大 double buffer 深度」是**竞争关系**，不是叠加关系：
两者都要 UB，谁拿得多谁就逼另一方退让。决定取舍要看哪一侧的停顿更贵。

## 触发症状

- `mte2_pct` 明显高于 `vec_pct`，瓶颈判定为 memory_bound
- 数据复用率高：同一块 GM 数据被 N 个 tile 读取，N 越大收益越大
- 该数据的总量小于单核可用 UB 扣除其他用途后的余量

反指征（出现这些时不要用）：
- 瓶颈已是 compute_bound —— 省搬运不会缩短总时间
- 待常驻数据超出 UB 余量 —— 会挤掉 double buffer，净效果可能为负

## 最小可运行例

结构上是把「每轮搬入 + 计算」改成「一次搬入 + 每轮只计算」：

```
改造前（每个 tile 都搬一次共享数据）
  for tile in tiles:
      DataCopy(shared_local, shared_gm, len)   <- 重复搬运
      DataCopy(tile_local,  tile_gm,   len)
      Compute(tile_local, shared_local)

改造后（共享数据常驻 UB）
  DataCopy(shared_local, shared_gm, len)       <- 只搬一次
  for tile in tiles:
      DataCopy(tile_local, tile_gm, len)
      Compute(tile_local, shared_local)
```

具体 API 形态与 UB 分配方式随算子而异，实施前请查
`ops/ascendc-performance-best-practices/reference/common/ub_resident_design.md`。

## 已知坑

- **UB 余量要按实际查，不要硬编码**。`npu-arch` 记载 DAV_2201 的 UB 为 192KB，
  但运行时必须用 `PlatformAscendC` 接口取实际值；不同子型号有差异。
- **Bank 冲突**。常驻块与每轮搬入块若落在同一 bank，访问会串行化，
  省下的搬运时间被冲突吃掉。上面那份参考文档里有规避方式。
- **收益会随 tile 数变化**。tile 少时复用次数少，改造收益可能低于噪声底，
  此时不应接受该变更。
- **与 double buffer 争 UB**。先量哪一侧停顿更贵再决定，不要两个都开满。
