# DAV_3510 架构事实与签名差异

> 事实来源：[`ops/npu-arch`](../../../../../ops/npu-arch/SKILL.md) 及其
> `references/npu-hardware-params.md`、`simt-arch-guide.md`。
> 本文件只做「架构事实 → 签名含义」的转译，不新增事实。
>
> **所有数值运行时必须以 `PlatformAscendC` 接口取得，禁止硬编码。**

## 覆盖范围

Ascend950 系列。相对 DAV_2201 的变化较大，架构可选择空间也更大，
因此 milestone 的决策图通常更深。

## 关键容量（典型值）

| Buffer | DAV_2201 | DAV_3510 | 影响 |
|---|---|---|---|
| L0C | 128 KB | **256 KB** | 单次 Cube 输出块可以更大 |
| UB | 192 KB | **248 KB** | 常驻与 double buffer 的争用没那么紧张 |
| BT | 1 KB | **4 KB** | — |

`Ascend950PR` 的 Cube 核数典型为 28（PCIE）或 32（Server），频率 1.65 GHz，
L2 为 112 MB / 128 MB。子型号差异见 `npu-hardware-params.md`。

注意频率比 DAV_2201 低：**跨代比较绝对时间没有意义**，只能比相对参考的
比率。这也是论文坚持同 job 配对计时的原因之一。

## 新增的架构可选项

这些是 DAV_2201 没有的，分析 DAV_3510 上的参考时要把它们纳入假设空间：

| 新增 | 对架构决策的意义 |
|---|---|
| **CV 直通通路**（L0C→UB、UB→L1、SSBuffer 消息） | 数据可以不经 GM 在核内流转，改变了「重算 vs 存储」的边界位置 |
| **BufferID 同步**（替代 set/wait 强配对） | 同步开销与编排方式不同，相关经验不可与 DAV_2201 互换 |
| **SIMT 编程模型** | 不规则操作（条件分支、离散索引）有了新的实现路径 |
| **SIMD-Regbase** | 寄存器组带来不同的代码形态 |
| **NDDMA** | 高维搬运可以一次完成，改变搬运次数的估算 |
| **CCU 通算融合** | 通信与计算的重叠方式 |
| **FP8 / MXFP8 / MXFP4 / HiF8 Cube MMAD** | 低精度矩阵运算，改变算力上限的计算基准 |

## 签名解读上的注意事项

### CV 直通会让搬运量的推断失准

在 DAV_2201 上，核间数据交换必然经过 GM，所以 MTE2/MTE3 的占比能较好地
反映数据流动总量。DAV_3510 有了直通通路后，**一部分数据流动不出现在
MTE2/MTE3 里**。

直接后果：看到 MTE2 占比低，不能直接推断「数据复用做得好」，也可能是
「走了直通通路」。这两种情况的后续优化方向完全不同。

需要用 `aic_fixpipe_ratio`、`aic_mte1_ratio` 等字段交叉验证，或者把它
列为开放问题。

### 低精度格式影响算力利用率的基准

用 `aic_cube_fops` 判断是否接近算力上限时，分母要用**对应数据格式的**
峰值算力。按 FP16 峰值去算一个跑 FP8 的 kernel，会得出「远未饱和」的
错误结论。

### MXFP 有 Tiling 约束

MXFP 格式对 tiling 有额外约束，见 `npu-arch` 的 `npu-arch-guide.md`。
若参考实现使用了 MXFP，它的 tile 形状选择可能是被这个约束决定的，
而不是性能权衡的结果 —— 这会改变 milestone 里该决策的 `purpose` 和 `cost`。

## 与 DAV_2201 的经验互通性

| 经验类型 | 可否互通 |
|---|---|
| 同步原语相关 | **否**（set/wait vs BufferID） |
| 数据通路相关 | **否**（有无 CV 直通） |
| 低精度格式相关 | **否**（本代新增） |
| 纯 UB 容量权衡 | 需重新量化（容量不同） |
| 搬运对齐、尾块处理等通用原则 | 通常可通，但仍需实测认证 |

知识库按架构分区就是在执行这张表。跨架构套用一条未经本架构认证的经验，
准入闸会拦下来。
