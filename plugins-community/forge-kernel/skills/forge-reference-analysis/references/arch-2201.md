# DAV_2201 架构事实与签名差异

> 事实来源：[`ops/npu-arch`](../../../../../ops/npu-arch/SKILL.md) 及其
> `references/npu-hardware-params.md`。本文件只做「架构事实 → 签名含义」
> 的转译，不新增事实。
>
> **所有数值运行时必须以 `PlatformAscendC` 接口取得，禁止硬编码。**
> 下面列出的典型值仅供分析参考实现时估算量级，不得写进 kernel。

## 覆盖范围

Ascend910B 系列。论文的 Ascend 跨架构实验跑在 910C 上，同属 DAV_2201 代。

## 关键容量（典型值）

| Buffer | 典型值 | 对架构决策的约束 |
|---|---|---|
| L0C | 128 KB | 限制单次 Cube 输出块大小 |
| UB | 192 KB | **最常成为架构决策的硬约束**：行常驻、double buffer、中间缓冲三者争它 |
| BT | 1 KB | — |

`Ascend910B2` 的 Cube 核数典型为 24，频率 1.8 GHz，L2 为 192 MB。
不同子型号有差异，见 `npu-hardware-params.md` 的子型号表。

## UB 是这一代最常见的架构约束

分析参考实现时，UB 余量往往就是它架构选择的解释。举例：

- 参考的 `Block Dim` 明显小于可用核数 → 很可能是单核要吃下某个常驻结构，
  不得不减核
- 参考没有开满 double buffer → 很可能是常驻结构已经占去大部分 UB

这些都是**可以写成决策的假设**，但要注意它们的 trigger 是间接的
（从 Block Dim 和占比推断），不是直接观测。写进 milestone 时要如实标注
推断链条，不要伪装成直接观测。

## 同步机制：set/wait 强配对

DAV_2201 使用 set/wait 强配对同步。这与 DAV_3510 的 BufferID 机制**不兼容**，
因此：

> 本架构下总结出的同步相关经验，**不得**直接套用到 DAV_3510。
> 知识库按架构分区正是为了防止这种误用。

## 签名解读上的注意事项

| 观测量 | 本架构下的特别说明 |
|---|---|
| `Mix Block Dim` | A2/A3 有效，可用来判断是否 MIX 算子 |
| 活跃带宽字段 | 仅 A2/A3 提供，可用来区分「搬运到极限」与「搬运效率差」 |
| CV 直通通路 | 本代**没有** L0C→UB、UB→L1 直通；若观测到的数据流看起来绕过了 GM，需重新检查推断 |

最后一条尤其要当心：把 DAV_3510 才有的通路套到本代的分析上，会推出一个
物理上不存在的架构。

## 数据格式

本代不支持 FP8 / MXFP8 / MXFP4 / HiF8 的 Cube MMAD（那是 DAV_3510 新增的）。
若参考实现看起来在做低精度矩阵运算，不要假设它用了这些格式。
